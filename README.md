# 需求分析 Skill

给 B 端产品经理用的一套需求分析方法，配一个会提问的 AI 助手。

---

## 我为什么需要它

B 端产品经理的日常大概是这样的：

> 业务方在群里甩一句"你们预约这块能不能加个导出"、"客户老说撞单，你看看怎么改一下"。

然后你面对两个都很糟的选择：

**直接开写。** 让 AI 半小时出一份 PRD，格式漂亮、章节完整、看着很专业。但里面每一条都是猜的 —— 客户到底被什么影响、这个问题多久发生一次、他们现在怎么应对、有没有线下土办法兜着，你一样都不知道。评审会上开发问"这个功能为什么存在"，你只能答"业务方提的"。真到上线，客户说"我要的不是这个"。

**先不写。** 但你也不知道该问什么。问"您觉得这个功能应该怎么做"——客户答不上来；问"您有什么需求"——客户给你讲一遍产品经理的脑回路。最后变成你一个人闷头想，想出来的东西没人拍板。

这个 skill 处理的就是这两难：**它不让 AI 替你想，它让 AI 逼着客户把话说清楚。**

---

## 核心思路

> **需求 = 预期 − 现状。**
>
> **我们是解决方案专家，客户只是问题专家。**

客户提的永远是**方案**（加个导出、做个筛选、支持批量），不是**问题**。方案背后的问题、频率、现状、约束、影响面，全都还是空白。

所以拿到需求的第一件事不是写文档，是**问**。问清楚了，你手上的方案可能自己就变了 —— 或者客户自己就否掉了。

这个 skill 把这套方法固化成了三件事：

| | 普通 AI 写 PRD | 这个 skill |
|---|---|---|
| **第一步** | 直接开始写 | 先反问你 5–8 个问题 |
| **写文档前** | 不设限，随时能出 PRD | **闸门锁死**，没答复就写不出 PRD |
| **文档质量** | 内容完整但来源不明 | 每条结论都标着**是客户确认的，还是我们猜的** |
| **需求变更时** | 全文重写，改漏了没人知道 | 编号体系能追到受影响的每一条 |

第四条是我自己用下来最值的地方 —— 需求评审通过了三个月，客户加一句"顺便把 X 也导出来"，你能立刻知道要连带改哪几条验收标准、哪几个测试用例，而不是靠记忆翻文档。

## 一次真实的分析长什么样

我拿之前做过的体检预约系统举例。原始输入是业务方的一句话：

> "前台说在系统里给每个时段加个人数上限就行了。"

**如果直接写 PRD**，你会得到一个"时段容量配置管理"模块：字段设计、页面原型、接口列表、默认值、权限控制。很完整，全是猜的。

**用这个 skill**，第一轮产出的是一份《需求澄清问题清单》，8 个问题，每个都带三样东西：

| 澄清目标 | 问题（节选） | 为什么问 |
|---|---|---|
| 问题有多真 | 最近一次"撞单"到底发生了什么？大概哪天、哪个时段、来了几位客人、前台最后怎么处理的？ | 把"约太多人"从一句感受变成一件可核对的事实 —— 不然分不清是时段总量超了、同一客户被重复预约，还是客人全挤在时段开头 |
| 问题有多痛 | 客人"等很久"，等的是哪一步、等了多久？ | 决定要限制的是"每时段总共放几人"还是"某个瓶颈资源的并行服务量" |
| 现状怎么办 | 现在有没有人在人为控制每时段人数？是口头交代、写纸上，还是纯凭经验？ | 如果这条规矩线下已经在执行，这事就变成"把既有规则搬进系统并让它可配置"，范围完全不同 |
| 谁的痛 | 除了前台和客人，抽血、导医这些同事有没有因为上午集中到店而排不开？谁有权拍板？ | 前台是提方案的人，不一定是被影响最重的人，也不一定有拍板权 |
| 方案前提 | 如果今天要定这个上限，凭什么定这个数？以后谁来调？ | 决定这个数是写死在代码里，还是业务可维护的参数 |

同时并行产出一份《访谈记录与假设登记册》，把已经知道的事实记成 `A-xx`，把**还没验证的推断**记成 `S-xx`，而且每条假设都强制写清楚两件事：

| 编号 | 假设内容 | 验证方式 | 验证不成立的后果 |
|---|---|---|---|
| S-01 | 现状不存在任何人工或系统层面的人数准入控制 | 查上周预约记录，问前台是否曾因人数超额劝退过客人 | 若实际已存在被默认执行的人工控制，需求实质是"把现行做法搬到系统里并让它可见"，取值口径必须沿用现行做法，不能另起一套阈值 |
| S-02 | 客人到店的等待时长目前没有被系统记录，只能靠前台回忆 | 查现有系统是否有叫号或等待时长记录 | 若其实已有可查的历史数据，可直接用作基线；若确无记录，第一阶段范围需先扩到"把等待记录下来"，否则改善效果无法证明 |

**"验证不成立的后果"这一栏是这个 skill 最反直觉、也最值钱的设计。** 写假设的时候顺手想一想"如果我猜错了会怎样"，你会发现自己对某些问题其实一无所知 —— 那这些地方就该在文档里明确标成待验证，而不是混在正文里当结论。

客户答完话，你才进入下一个阶段：出干系人档案、业务流程、业务场景、问题卡片、管控点、领域模型、功能清单、验收标准…… 每一条都挂着来源。

**整个过程里，AI 始终在提问和整理，没替你编过一条业务事实。**

## 阶段闸门

写需求最常见的翻车不是写不出来，是**写太快**。调研没做完就落 PRD，猜的结论跟确认的事实混在一起，后面谁也分不清哪条能信。

所以这个 skill 用了硬闸门 —— 不是提醒你，是**脚本会报错拦住**：

| 阶段 | 允许产出 | 禁止产出 |
|---|---|---|
| **G0 还没提问** | 《需求澄清问题清单》《访谈记录与假设登记册》 | 任何其他文件 |
| **G1 问了、还没收到答复** | 同上两份，可以追加新问题 | 问题卡片、干系人档案、流程、场景、模型、功能清单、PRD —— **包括标着"分析底稿""初稿""供讨论"的** |
| **G2 收到第一轮答复** | 可以写分析底稿，但每条必须标 `A-xx`（客户确认的）或 `S-xx`（我们假设的） | 没标来源的结论 |
| **G3 澄清完成** | 全套产物 | —— |

"分析底稿"不是后门。我见过太多 PRD 里的功能需求挂着"待确认"三个字就当自己过关了 —— 但那只是**可追溯性**解决了，**该不该写**没解决。G1 阶段写下的功能需求会被下游整条链继承，一处猜，全链错。

进 G2 也不需要等所有问题都答完。核心问题（谁提的、谁的什么问题、现在怎么应对、多久一次、必答三问）**答完 5 项以上**就能进；没答的问题，对应的内容**一路保留 `S-xx` 标注**带到验收标准和测试用例里。

## 你会拿到哪些产物

| 产物 | 回答什么问题 | 给谁看 |
|---|---|---|
| 需求澄清问题清单 | 我们到底还不清楚什么 | 客户 / 业务方 |
| 访谈记录与假设登记册 | 哪些是客户确认的，哪些是我们猜的 | 你自己 / 项目组 |
| 问题卡片 | 这个业务问题有多痛、多急、值不值得做 | 评审会 |
| 干系人档案（含阻力点） | 谁受益、谁受损、谁反对、谁能拍板 | 评审会 / 项目经理 |
| 业务流程列表 / 业务场景 | 事情现在是怎么跑的，问题出在哪个环节 | 开发 |
| 管控点分析 + 业务报表 | 管理上要看什么数、从哪看 | 业务负责人 |
| 领域模型 / 业务数据描述 | 系统里有哪些对象、哪些数据 | 开发 / 数据 |
| 功能需求清单 / 质量需求 | 要做什么、要做得多好 | 开发 / 测试 |
| 业务规则 / 约束 | 什么必须成立、什么不能碰 | 开发 / 测试 |
| 验收标准 | 怎么算做完了 | 测试 / 客户 |
| 需求规格说明书 | 汇总上述全部 | 全体 |

日常的小变更（改个字段、加个筛选）不用全套走一遍，模板在 `templates/daily-change.md`。

## 编号体系

所有产物用同一套编号串起来，这样任何一条结论都能回溯到它的出处，任何一次变更都能定位到受影响的范围。

| 前缀 | 含义 | 归属产物 |
|---|---|---|
| `Q-xx` | 待答复的问题 | 问题清单 |
| `A-xx` | 客户已确认的事实 | 访谈记录（**全项目唯一定义处**） |
| `S-xx` | 我们的假设（须写明验证方式与不成立后果） | 访谈记录（**全项目唯一定义处**） |
| `T-xx` | 业务术语的当前口径 | 访谈记录 |
| `PC-xx` | 问题卡片 | 问题卡片 |
| `SD-xx` / `SP-xx` | 干系人 / 阻力点 | 干系人档案 |
| `CP-xx` | 管控点 | 管控点分析 |
| `FP-xx` | 业务流程 | 业务流程列表 |
| `US-xx` | 业务场景 | 业务场景描述 |
| `BR-xx` | 业务规则 | 业务规则描述 |
| `DC-xx` | 领域类 | 领域模型 |
| `QS-xx` | 质量场景 | 质量场景决策卡 |
| `MR-xx` | 维护场景 | 维护需求描述 |
| `C-xx` | 约束 | 约束描述 |
| `F-xx` | 功能需求 | 功能需求清单 |
| `NFR-xx` | 非功能需求 | 质量需求 |
| `AC-xx` | 验收标准 | 验收标准 |

一个前缀只指代一件事。已被占用就换一个（比如 `RN-xx` 给阻力点），**不要复用** —— 复用了读者就分不清 `S-02` 到底是哪个。

## 自检脚本

每个阶段跑一次，用对应参数（阶段不同，查的东西不同）：

```bash
python3 scripts/check_artifacts.py <产物目录> --stage G1   # 闸门自检
python3 scripts/check_artifacts.py <产物目录> --stage G2   # 编号闭合 + 溯源 + 假设合规
python3 scripts/check_artifacts.py <产物目录> --stage G3   # 全部检查（加撞号与措辞一致性）
```

退出码：`0` = 通过，`1` = 发现问题，`2` = 用法/目录错误。

### G1 闸门：管的是内容，不只是管文件数量

只允许《需求澄清问题清单》《访谈记录与假设登记册》各一份，且内容必须干净。命中以下任一即报错：

1. 标题出现"业务流程 / 领域模型 / 功能清单 / 问题卡片"等分析产物名
2. 表头出现"步骤 / 责任人 / 模块 / 场景"等分析结论特征词
3. 出现 `Q/A/S/T` 之外的前缀编号（`FP-01` / `US-01` / `D-01`…，定义或引用都算）
4. 正文出现"该系统应包含…"这类强断言
5. 代码块里画了流程图
6. 出现无编号的清单式条目

**换个标题躲不掉。** 把"功能清单"改叫"附：本次要做的"，只要内容形态还是分析结论，一样会被抓出来 —— 第 6 条就是专门堵这个的。

### G2：编号闭合 + 溯源 + 假设合规

- **编号闭合** —— 被引用的编号必须有定义，不许有悬空引用
- **溯源完整** —— `F-xx` / `NFR-xx` / `AC-xx` / `MR-xx` 必须带 `A-xx` 或 `S-xx`
- **假设纯度** —— 假设只能是"是/否"型判断，不是一套结构（"审批流应设计为单级节点，状态机含四态"这种是分析结论，不是假设）
- **假设登记两列** —— 「验证方式」和「验证不成立的后果」必须存在且非空，空着等于没写
- **前缀撞号** —— 同一前缀在两套不相干的编号体系里指代两件事

> 溯源只对**需求条目**强制。`BR-xx` 业务规则、`US-xx` 业务场景、`PC-xx` 问题卡片这些是**分析产物**，引用上游事实或分析结论就行，不要求直达 `A-xx` —— 否则会把"经分析推出的业务规则"错判成漏溯源。

### 撞号 vs 引用

同一编号在多份产物里出现**本身不是问题** —— 需求规格说明书、优先级评估、变更分析表都会复述上游编号，那是**引用**。脚本按**语义角色**判断归属：看这条记录**待在哪一栏**（表头列名 / 上级章节），不看它叫什么名字。

- 同一前缀在两套不相干的体系里指代两件事 → **报错**（真错）
- 同一编号在多份产物里出现但同体系 → 不报错；措辞不同 → **提示**（引用允许换措辞，但不能改所指）

## 怎么用

在支持 skill 的编辑器 / CLI 里直接提需求就行，比如：

> 体检预约系统最近老撞单，前台说在系统里给每个时段加个人数上限就行了，帮我把这个需求理清楚。

skill 会：

1. 问你 5–8 个问题（有抓手的，能直接回答的），同时把已经知道的事实和待验证的假设登记好
2. 你回答 → 它把答复落成 `A-xx`，把还问不出来的落成 `S-xx`
3. 进入分析，产出全套文档，每条标着来源
4. 每个阶段跑一次自检，把不干净的地方挡下来

**在你回答第一个问题之前，它不会写任何 PRD。** 这不是流程仪式 —— 没有访谈，问题级需求只能靠猜，猜错的部分会以"已确认需求"的形态混进文档，后期无法追溯、无法返工、无法验证。

## 适合什么，不适合什么

**适合**：
- B 端系统的**新系统建设**、**流程优化**、**客户投诉驱动的改进**
- 需求方自己也说不清要什么的时候
- 需求要过评审、要能对开发讲清楚"为什么做"
- 长期项目，需求会反复变，需要能追溯影响面

**不太适合**：
- 纯 C 端增长玩法（AB 实验、埋点、留存策略）
- 已经有成熟 PRD、只想要排版或翻译的
- 老板已经拍好方案、只需要你落成文档的（那闸门会挡你 —— 但这种情况通常正是最需要闸门的）

## 安装

```bash
git clone https://github.com/yangdavip/effective-requirements-analysis-skill.git \
  ~/.skills-manager/skills/effective-requirements-analysis
```

软链到对应 harness 的 skills 目录：

```bash

  ~/.workbuddy/skills/effective-requirements-analysis      # WorkBuddy
```

## 关于

这套方法最初是从一本 B 端需求分析的书里整理出来的（[《有效需求分析（第 2 版）》，徐锋著，电子工业出版社出版](https://www.cip.com.cn)），后来我发现书里的东西如果只是"读过"，实际干活时根本记不住哪些步骤不能省 —— 所以把它固化成了这个 skill：书里那条"没访谈清楚不许写 PRD"的规矩，在这里是一个会真的报错的脚本。
