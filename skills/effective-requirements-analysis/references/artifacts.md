# 产物模板

每个模板给出栏目、填写说明与要点。文件名以 `<系统名>_<产物名>.md` 命名。

产物清单（17 项任务 → 13 类产物）：

| # | 产物 | 来自任务 | 必需 |
|---|---|---|---|
| 1 | 问题卡片 | 目标/愿景分析 | ✅ 必填 |
| 2 | 干系人列表 | 干系人识别 | ✅ 必填 |
| 3 | 干系人档案 | 干系人分析 | 干系人多时必填 |
| 4 | 业务子系统描述 | 业务子系统划分 | 系统复杂时 |
| 5 | 业务接口分析 | 业务接口分析 | 多子系统时 |
| 6 | 业务流程列表 | 业务流程识别 | ✅ 必填 |
| 7 | 业务流程图模型 | 业务流程分析与优化 | ✅ 必填 |
| 8 | 业务场景描述 | 业务场景识别 | ✅ 必填 |
| 9 | 业务场景分析 | 业务场景分析 | ✅ 必填 |
| 10 | 管控点列表与分析 | 管理需求分析 | 有报表需求时 |
| 11 | 业务报表描述 | 业务报表分析 | 有报表需求时 |
| 12 | 维护需求描述 | 维护需求分析 | ✅ 必填 |
| 13 | 领域类图片段 / 领域模型 | 领域建模 | 必填 |
| 14 | 业务数据描述 | 业务数据分析 | 必填 |

## 1. 问题卡片

**一张卡片只写一个目标场景**，有多个场景就写多张。

| 栏目 | 填写说明 | 必填 |
|---|---|---|
| 问题描述 | 从业务事实与业务后果两方面客观描述。守业务态、客观性、匹配性 | ✅ |
| 频率 | 该问题发生的频率 | |
| 厌恶度 | 产生后果的影响度 | |
| 可替代性 | 当前是否有替代解决方案 | |
| 方案说明 | 从黑盒或灰盒视角阐述解决方案，帮助业务方建立宏观认知 | ✅ |
| 预期结果 | 方案投产后能达成的结果 | ✅ |
| 价值主张 | "一句话目标"，措施 + 效果结构。可作为需求规格说明书小节标题 | |

**填写要点**

- 频率是相对概念：与所属业务场景的频率级（秒级/多秒级/分钟级/多分钟级/小时级/多小时级/天级/多天级/周级）**差小于 3 级**的都算高频。例："办理入住"是多分钟级，天级算高频，大于天级算低频。
- 描述问题不要从系统角度写。"原有系统经常数据不一致"是系统视角；"当前各种借助系统生成的业务报表，存在统计口径不一、业务相关数据不一致的现象"是业务视角。
- 一句话目标示例：
  - ❌ "构建物资管理系统，避免物资脱节"（措施不够业务态，效果无价值态）
  - ✅ "基于安全库存避免物资脱节，为门店扩张奠定后勤基础"

## 2. 干系人列表

| 栏目 | 填写说明 |
|---|---|
| 类型 | 出资人/发起人、使用者、评价者、其他 |
| 名称 | 通常以职位或角色描述 |
| 说明 | 为什么他是关键或重要干系人 |
| 相关度 | 高/中/低 —— 项目与他直接相关吗？涉及他的利益或责任吗？ |
| 影响度 | 高/中/低 —— 他对项目方向、验收有很强影响力吗？ |

**相关度与影响度通常仅供开发团队内部阅读，不宜直接提供给客户代表**，避免"为什么说我的相关度低"这类麻烦。

## 3. 干系人档案

**一张档案只写一个干系人。**

### 基本信息

| 栏目 | 说明 |
|---|---|
| 名称 | |
| 类别 | 与干系人列表的类别相同 |
| 相关度 / 影响度 | 仅供内部 |
| 职责 | 工作职责要点，用于理解其关注点的角色基础 |
| 代表 | 多个干系人中选定的代表 |
| 联系方式 | |

### 核心关注点

逐条写出，每条编号以便跟踪，并判重要度（高/中/低 或 关键/重要/有用/一般）：

| 编号 | 关注点（正需求） | 对应功能需求 | 重要度 |
|---|---|---|---|

| 编号 | 阻力点（负需求） | 应对措施 | 重要度 |
|---|---|---|---|

**阻力点用"避免…"间接表述**，避免影响客户阅读时的情绪。

### 备注

专业背景、职业发展过程等便于理解干系人的信息。

| 类型 | 主业务流程 / 变体业务流程 / 支撑业务流程 / 管理流程 |

## 7. 业务流程图模型

按分层原则绘制：**部门级流程**（岗位间协作）—— 需求分析在这一粒度进行。

自检两条：是否与协作无关？是否不是独立可汇报的工作单元？命中任一条则应下沉到个人级流程。

流程须体现**八要素**：分工、活动、协作、产物关系、分支（基本）＋ 审批、规则、异常（管理）。

## 10. 管控点列表与分析

**管控点列表**（每个子系统一份）

| 栏目 | 说明 |
|---|---|
| 类型 | 经营类 / 管理类（可细到下级分类） |

**管控点分析**

| 栏目 | 说明 |
|---|---|
| 相关干系人 | 哪些管理层用户会使用；阅读重心不同则用文字指出 |
| 管控点目标 | 从业务角度、以价值态说明各干系人希望通过此管控点达到的业务目标 |

| BI / 数据仓库 / 数据挖掘需求 | 报表无法实现的部分，以黑盒视角明确需求 |

## 13. 领域类图片段 / 系统领域模型

### 领域类图片段

三部分：

1. **领域类图片段** —— 图形部分，附图例
2. **业务数据说明** —— 指出别名，说明意义
3. **数据规则** —— 与该数据相关的规则

### 系统领域模型

合并所有片段后的总图。合并时：

- 合并"不同名、实际相同"的类
- 优化关系（适度处理传递依赖等复杂关系）、补充各领域类的关键字段

**自检四问**：缺红色吗（不可能没有需要记录的动作）？缺绿色吗（总会涉及人、地点、东西）？缺黄色吗（那就不灵活了）？缺蓝色吗（那说明可配置性太差）？

## 15. 关键质量需求列表 + 质量场景决策卡

### 关键质量需求列表

| 栏目 | 说明 |
|---|---|
| 质量目标类型 | 安全性 / 可靠性 / 易用性 / 性能 / 可维护性 / 可移植性 |
| 质量目标子类 | 如访问安全性、数据安全性、易学性、易操作性、适应性 |
| 说明 | 为什么重要 |

排序依据：**风险曝光度 = 威胁影响度 × 出现频率**（频率：经常 3 / 偶尔 2 / 低概率 1）。

### 质量场景决策卡（目标场景决策卡）

| 栏目 | 说明 |
|---|---|
| 目标 | 属于哪种质量类型 |
| 场景 | 影响质量需求的具体场景 |
| 策略 | 针对该场景采取的技术措施 |
| 风险 | 该措施带来的负作用 |
| 冲突平衡 | 与其他质量场景对策的冲突及取舍 |

**每个质量场景都要写"风险"栏** —— 漏掉它就等于没做冲突分析。

## 16. 业务规则描述

按**作用域**（宏观/中观/微观）与**类型**（行为类/数据类/权限类）双重归类。

| 规则编号 | 规则内容 | 类型 | 作用域 | 业务动机 | 可执行性考虑 |
|---|---|---|---|---|---|

**业务动机与可执行性两栏是本产物的价值所在**，填不出说明尚未真正理解这条规则。

## 17. 项目约束 / 设计约束

### 项目约束描述

| 栏目 | 说明 |
|---|---|
| 进度要求 | 最晚交付时间 **及其背后的理由**（新业务上线？新法规实施？展会？） |
| 资源支持 | 接口人、开发/测试环境支持 |
| 预算要求 | 通常参考合同约定 |

### 设计约束描述

| 栏目 | 说明 |
|---|---|
| 技术选型 | 注明是**不可改变**（法规/政策/内部规范）还是**可协商**（接口人个人偏好） |
| 部署环境 | 遗留系统、软硬件平台、国家/文化区域、生命周期长度 |
| 开发环境 | 通常不在需求分析阶段明确 |
