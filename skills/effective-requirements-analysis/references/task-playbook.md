# 17 项关键任务执行要点

组织应用类软件需求分析的全景：两个层次（价值需求 / 详细需求），四条主线（价值 / 功能 / 数据 / 非功能）。

**任务板是帮助理解该从哪些角度分析的工具，不是必须填满每一栏的表单。** 试着把每栏都填上，你就成了工具的奴隶。

## 全景

```
价值需求主线   目标场景 ─→ 干系人关注点 ─→ 干系人阻力点
                （黑盒视角：整个系统为客户解决了什么问题、创造了什么机会）

详细需求主线
  功能需求   业务支持 ── 业务流程 ── 业务场景 ── 场景分析
             管理支持 ── 管控点 ── 业务报表
             维护支持 ── 维护场景
  数据需求   范围与关系（领域建模）── 构成与推演（业务数据分析）
  非功能需求 关键质量属性 ── 质量场景 ＋ 约束
补充内容     业务规则、约束
```

**识别出五类最小需求单元**：业务功能、业务报表、业务数据、质量场景、业务接口。

## 价值需求主线

### 1. 目标/愿景分析 → 《问题卡片》

回答三个本质问题：整个系统为客户解决了什么问题、创造了什么机会？最关键的干系人有哪些？他们关注什么、担心什么？

- 关键：**需求 = 预期 − 现状**，目标 = 问题 + 机会
- 目标三种描述：**定性**（空洞，避免）、**定量**（SMART：具体、可衡量、可实现、有相关性、有时限）、**场景化**（推荐：真实、易懂、可验证、有感染力）
- 场景化描述三段式：①问题（列举真实故事）②影响谁/后果（分析业务损失）③解决方案要点
- 定义问题三要点：**业务态、客观性、匹配性**
- 分析影响三要点：**指代清晰（具体到人，不用"客户""管理层"）、视角匹配、推理合理（呈现推理过程）**
- 解决方案策略化 —— 写具体策略而非空话，也不宜直接写功能模块
- 提炼**一句话目标**：以"措施 + 效果"结构，同时体现业务态与价值态
- 例："基于安全库存避免物资脱节，为门店扩张奠定后勤基础"（合格）；"构建物资管理系统，避免物资脱节"（不合格）
- 剪裁：法规强制改造、新业务上线、增加新渠道 → 可跳过，但需谨慎

### 2. 干系人识别 → 《干系人列表》

根据目标识别 + 根据风险补充。**不追求列得全，追求列得准。**

类型：出资人/发起人、使用者、评价者（财务、审计、法规、行业监管，通常有一票否决权）、其他（开发、维护、领域专家、技术专家）。

**相关度**与**影响度**分别评估。注意相关度低而影响度高的人，其真实需求优先级往往很低（会上随口提的边缘反馈）。

### 3. 干系人分析 → 《干系人档案》

选代表（代表性 + 典型性）→ 访谈收集 → 分析关注点（正需求）与阻力点（负需求）→ 横向识别关注点冲突并制订应对策略。

干系人档案：基本信息（名称、类别、相关度、影响度、职责、代表、联系方式）＋ 核心关注点（逐条编号、判重要度）＋ 备注。

阻力点用"避免…"表述，不影响客户阅读情绪。

剪裁：干系人少且关注点简单明确时，可省档案，直接写在列表的"说明"栏。

### 4. 价值需求分析总结（串讲）

三个子任务是**同时执行**的有机整体，不是串行。

正确顺序：**先找痛点 → 厘清问题事实 → 分析业务后果 → 初步拟定解决方案概念 → 展望价值 → 再围绕这个方案识别干系人 → 分析其关注点与阻力点**。

发现一个痛点就完成一轮；系统通常有多个痛点，过程重复多次。

**要点**：干系人识别围绕痛点与方案展开，不追求列全；负需求不是"负面的需求"，而是系统建设带来的影响，需在方案与功能设计上缓解。

## 系统分解

### 5. 业务子系统划分 → 《系统分解模型》

目的**控制复杂度**，不是为了分解而分解。系统简单、用户群单一时可剪裁。

**必须按业务视角划分，不按技术实现划分** —— 技术视角会让用户无法参与、无法建立全局观、无法判断完整性。

划分策略：

| 策略 | 适用 |
|---|---|
| 按业务职能（部门职能） | 支撑、管理型系统的最典型策略（产、销、供、管） |
| 按产品/服务 | 外部服务系统；内部平台可按审批类型等变通 |
| 双维度 | 复杂系统：先用产品/服务一级划分，再用职能二级划分 |
| 按关键特性 | 计算机域主题系统（安防、楼宇自控）—— 从价值角度识别关键特性 |
| 分析对遗留系统的影响 | 遗留系统改造：新增哪些、修改哪些、影响哪些 |

**标识接口、确定关系**：两两子系统之间讨论"我们需要对方提供什么服务？我们能为对方提供什么服务？"，用**动宾结构**命名，说明谁提供、谁使用。哪里有分解，哪里就有接口。

呈现方式：**层次图**（纵向分解，关系简单时）、**构件图**（有横向服务/调用关系时，推荐）、**数据流图**（主要是数据共享交换时）。

> 检验标准：如果你的划分结果是"智能传感器系统、录像系统、报警系统"，那是技术视角；用户视角应是"防盗子系统、灾害预警子系统、家庭看管子系统"。

### 6. 业务接口分析 → 《业务接口分析》

业务接口 ≠ 系统接口设计。一个业务接口可由一个或多个系统接口实现；业务接口只明确 **Why（用途与业务价值）、What（交互过程）** 及约束，不涉及 How。

三个问题：

1. **接口由哪个子系统实现更合理** —— "知行合一"原则：由"知"接口所需信息的子系统来实现（"反馈物资使用情况"由物资管理子系统实现，而非反馈物资的体检业务子系统）
2. **哪些子系统会用它、达成什么业务价值、什么时机、什么频率**
3. **使用频率** —— 给出典型频率值

交互过程用时序图，数据包用数据词典。约束：协议要求、性能要求、部署环境、使用者特点。

只要存在多个业务子系统（含修改、影响的）就必须执行。修改既有接口时，先说明原接口，再说明修改要求与理由。

## 功能需求主线 · 业务支持

### 7. 业务流程识别 → 《业务流程列表》

**先外后内、先业务后管理**：

1. 识别外部客户 → 主、变、支流程
2. 识别外部员工、内部员工、触发流程的特定时间/状态 → 主、变、支流程
3. 识别管理流程（事前预防 / 事中控制 / 事后分析）
4. 判断流程优先级（主营业务 × 发生频率 → 关键/重要/有用/一般，可加"镀金"）

**主、变、支** 的分类只为保证识别全，不必纠结归属。变体流程相对独立、无法整合进同一张流程图。

管理流程识别角度：业务上线类的审批控制；人财物资源管控；进度和异常控制。

剪裁：单一用户、以人机交互为主的系统（如 POS）可跳过流程识别与流程分析，直接做业务场景识别。

### 8. 业务流程分析与优化 → 《流程图模型》

**分层原则**（关键）：

| 层级 | 画什么 | 读者 |
|---|---|---|
| 组织级流程 | 部门间协作 | 决策层 |
| 部门级流程 | 岗位间协作 | 管理层 ← **需求分析在这一粒度进行** |
| 个人级流程 | 一个岗位的工作步骤 | 在业务场景分析时再细化 |

判断流程图是否画得过细的两条原则：**是否与协作无关**、**是否不是独立可汇报的工作单元**。

**八要素**：五个基本要素（分工、活动、协作、产物关系、分支）＋ 三个管理要素（审批、规则、异常）。

分工的三个来源：**规模、风险、专业**。

### 9. 业务场景识别 → 《业务流程内业务场景描述》

从流程分拆场景，命名 **"角色：业务场景（动宾格式）"**。每个场景是相对独立、可暂停、有价值、可汇报、通常不再分拆的业务活动。

识别完后按流程优先级 + 场景是否必备 + 依赖关系排序。

呈现：用例图（推荐，管理者看事到事逻辑、操作层看人到事逻辑，二者结合）、业务场景列表（不想用"用例"概念时）。

**此项不可剪裁**（纯数据分析系统除外），它是"封装需求的分子单位"。

### 10. 业务场景分析 → 《业务场景分析》

"场景—挑战—方案"逻辑，取代"输入—输出—处理"。五步：

1. 概述业务场景 —— 用户要达成什么业务目的（用用户语言写意图）、前提条件与后置条件（各约 30% 的场景存在）、除执行者外还有谁关心它
2. 细化业务步骤 —— 基本事件流、扩展事件流、异常事件流
3. 遍历步骤分析困难，导出功能 —— 每一步用户会遇到什么困难 → 系统需要提供什么功能；再问"是否存在不能按以上步骤处理的关键例外"
4. 识别环境与规则 —— 性能相关（人数、典型业务量、峰值、密度）、易用性相关（用户成长经历与相关系统使用经验）、部署环境相关
5. 分析实现方式，完成初步交互设计 —— 交互过程、静态快照、设计说明（是建议还是约束）

**写作要点**：写用户意图而非用户动作；写人机交互而非人机界面；不用"如果…那么…"（改扩展事件流）；不用"重复执行…"（改子事件流）；编号扩展点 `2a`/`2b`。

**此项不可剪裁**。

## 功能需求主线 · 管理支持

### 11. 管理需求分析 → 《管控点列表》《管控点分析》

管理支持三个面向：**事前风险规避**（增加管理流程）、**事中风险控制**（规则与审批）、**事后总结优化**（数据分析）。前两者在业务支持分析中统一处理，数据分析是本任务核心。

三层逻辑：**管控点（Why）→ 指标 → 报表/BI/数据挖掘（How）**。指标层不可跳过，它是两者的桥。指标与管控点是**多对多**关系（排队时间既可分析业务设置合理性，也可分析客户满意度）。

识别步骤：标识管理者（决策层/管理层/经营型 vs 管理型）→ 标识管控点 → 分析指标体系 → 明确实现方式与数据收集需求。

三种识别方法：**职责分析**（职位职责与考核指标）、**问题分析**（管理型从管理问题、经营型从经营问题入手）、**案例借鉴**（同行与相关行业的数据分析应用）。

指标分析要**正反两面**思考：正面"需要哪些信息"，反面"如果不合理会出现什么情况，能由哪些数据反映"。

实现方式取决于：数据源是否固定、查询条件是否固定 → 固定则用报表，否则用 BI / 数据仓库 / 数据挖掘。

命名：管控点名称应体现意图，**避免"统计""汇总"等技术性动词**。

剪裁：不含数据分析支持管理的系统可剪裁；经营分析/大数据项目则是重中之重。

### 12. 业务报表分析 → 《业务报表描述》

报表分析要从**管控点**出发，不是从"客户想要什么报表"出发 —— 用户很难在需求分析阶段说清报表需求。

三部分：

1. **报表概述** —— 谁使用（区分报表生成者与阅读者，生成者可能出于考核压力伪造数据，需在实现层面应对）、为什么用（追溯到管控点的子意图）、使用频率如何（频率决定性能要求）
2. **报表内容** —— 输入条件、数据来源（哪些数据表、统计口径）、数据项及其格式与计算方法
3. **输出要求** —— 打印版与屏幕版差异、图表黑白打印的清晰度、分类小计、多页页码与表头、特殊排序需求

## 功能需求主线 · 维护支持

### 13. 维护需求分析 → 《维护需求描述》

**不要从功能实现角度列举，要从维护场景角度。** 不是"日志"功能，而是"排错"场景。

典型维护场景：

- **配置性** —— 从变化入手：用户群变化（职位、权限 → 功能权限/数据范围权限/分配权限）、流程变化、数据变化、法规变化
- **运行时（正常）** —— 运行状态监控（服务、网络通信、数据库、客户端）、数据备份（备份内容、周期、远程灾备、恢复）
- **运行时（故障）** —— 故障定位、排错、故障恢复、应急措施
- **其他** —— 系统初始化（安装、初始化配置、测试工具）、系统升级（远程、自动化、版本检查）、系统迁移（数据迁移、双系统并行）

维护场景**可在同类系统中重复使用**，每个项目只需少量修改。

剪裁：生命周期很短的临时/过渡系统可剪裁，其余通常必做。

## 数据需求主线

### 14. 领域建模 → 《领域类图片段》《系统领域模型》

数据需求主线厘清组织中的"信息流"。两个问题：**哪些业务数据要纳入系统（范围）**、**它们之间是什么关系**。

方法：**四色建模法**，按 **红 → 绿、黄 → 蓝** 顺序：

1. 红 —— 过程数据（需要存储的行为）
2. 绿 —— 自然数据（人、地点、东西）；黄 —— 角色数据（同一主体多种身份且不会相互转换）
3. 蓝 —— 描述类数据（概述类、规则类）

**自底向上**：找所有主业务流程 → 每个流程画一张领域类图片段 → 合并成系统领域模型。合并时要做两件事：合并"不同名、实际相同"的类；优化关系、补充关键字段。

**类图读法三要点**：用用户母语（中文）命名类与字段；给图配图例；**用业务语言读图**。

> "一个客户可以下多个订单；每个订单上有且只有一个收货人；订单是由订单项组成的；由于订单中涉及多个供应商，因此需将订单分拆成多个送货单……"
> 而非："客户和订单是一对多关系，订单和收货人是一对一关系……"

类间关系在领域建模阶段常用 4 种：关联、类别（泛化）、聚合、组合。**判断聚合还是组合：个体能否独立于整体而存在**（删部门不会删员工 → 聚合；删订单会删订单项 → 组合）。**关系是针对特定问题域/系统而言的**，离开系统环境谈关系没有意义。

**此任务必须执行的情形**：问题域对开发团队陌生；业务数据超过 50 个；直接做数据库设计困难。

### 15. 业务数据分析 → 《业务数据描述》

对每个业务数据做三类分析：

- **数据应用分析** —— 哪些流程用、用哪些部分、CRUD 关系
- **数据构成分析** —— 每个字段的类型、规格（长度/精度）、约束/取值范围、是否非空/键值/自动编号、计算字段的公式
- **数据特点分析** —— 主要/次要字段（决定列表显示什么）、稳定/不稳定字段（决定表结构扩展性）、即时/历史数据（决定迁移策略）、关键/辅助字段（决定索引）

除纯计算类系统外，此任务不可剪裁。

## 非功能需求主线

### 16. 质量需求分析 → 《关键质量需求列表》《质量场景决策卡》

**核心是逆向思维 + 场景化思维**，从威胁入手。

1. **识别关键质量属性** —— 安全性、可靠性、易用性、性能、可维护性、可移植性（可再分子类，如访问安全性、数据安全性、易学性、易操作性、适应性）
2. **排序** —— 风险曝光度 = 威胁影响度 × 出现频率（经常 3 / 偶尔 2 / 低概率 1）
3. **识别质量场景** —— 从用户心理预期、应用场景限制、运行环境约束三个角度
4. **识别冲突并平衡** —— 每项对策都会带来新问题，必须评估负作用并可能更换对策

**三种失败写法及破解**：

| 失败 | 例 | 破解 |
|---|---|---|
| 定性之败 | "高可靠、高易用、高扩展" | 场景化：写出具体会发生的场景。"高扩展性"要说明应对哪种变化（业务流程/法规/业务模式） |
| 定量之伤 | "平均无故障时间 2756 小时" | 为量化而量化（CMMI 考核）无意义。量化前提是**积累历史数据**。写不出精确指标时，**写使用频率比写拍脑袋指标更有用** |
| 全局化之迷 | "所有查询都在 7 秒内响应" | 全局描述难免以偏概全。区分场景；高频查询给更严指标 |

剪裁：除过渡性、演示性系统外不宜完全剪裁，至少应确定最重要的 3–5 项质量需求。

### 17. 约束分析 → 《项目约束描述》《设计约束描述》

非功能需求含**质量**与**约束**两类：质量是对我们的要求，约束是对我们的限制。

**项目约束**（客户决策层也关注）：进度要求（并理解最后期限背后的理由，以便指导分阶段交付及未能满足时的预案）、资源支持（接口人、开发测试环境；争取每个业务主题设业务接口人）、预算要求。

**设计约束**（信息部门关注）：技术选型（区分**不可改变**的法规/政策/内部规范，与**可协商**的接口人个人偏好）、部署环境（遗留系统、软硬件平台、国家与文化区域、生命周期长度）、开发环境（通常不必在需求分析阶段明确）。

## 补充

### 业务规则分析 → 《业务规则描述》

规则量大而复杂时单独作为专题；否则在流程分析、场景分析、领域建模时附带分析。

按**作用域**归类（宏观影响整个问题域 / 中观影响一个流程 / 微观影响一个场景），再按**类型**二次归类（行为类 / 数据类 / 权限类）。

**最重要的是分析规则背后的动机**（业务动机 + 可执行性考虑），它往往能发现规则欠考虑之处，并给出更优的规则方案。

## 剪裁速查表

| 任务 | 可剪裁条件 |
|---|---|
| 目标/愿景分析 | 法规强制改造 / 新业务上线 / 新增渠道 —— 谨慎 |
| 干系人识别 | **不可剪裁** |
| 干系人分析 | 干系人少且关注点简单时，可并入列表"说明"栏 |
| 业务子系统划分 | 业务简单、用户群单一 |
| 业务接口分析 | 存在多个业务子系统即须执行 |
| 业务流程识别 / 分析 | 单一用户、以人机交互为主的系统（POS 等） |
| 业务场景识别 / 分析 | **不可剪裁**（纯数据分析系统除外） |
| 管理需求分析 | 系统不含数据分析支持管理时 |
| 业务报表分析 | 系统无报表需求时 |
| 维护需求分析 | 生命周期很短的临时/过渡系统 |
| 领域建模 | 问题域陌生 / 数据 > 50 个 / 库设计困难 → **必须执行** |
| 业务数据分析 | 纯计算类系统（计算器等） |
| 质量需求分析 | 过渡性、演示性系统；否则至少定 3–5 项 |
| 业务规则分析 | 通常并入其他任务 |
| 约束分析 | 一般不剪裁 |

## 根据产品阶段选择主评估维度

| 阶段 | 主维度 |
|---|---|
| 0→1 建设期 | 业务维（价值-频率双维评估法） |
| 1→10 发展期 | 用户维、竞争维 |
| 10→100 成熟期 | 运营维（北极星指标、RFM 模型） |

或组合使用：每次迭代完成业务维 Top 3 + 竞争维 Top 3 + 运营维 Top 1。

**不要按四维分别评估再加权** —— 很多需求在某维度低价值而在其他维度高价值，一平均就被埋没。

结果分四级：**必须做 / 应该做 / 可以做 / 可不做**。
